# 关系提交、完整备份与恢复

YAML 仍是可手工编辑的运行资料；`runtime/state.sqlite3` 包含长期去重、额度和动作账本，不能当缓存删除。`cache/parsed.sqlite3` 才是可丢弃、可重建的解析索引。

关系更新先在同一 SQLite 事务中保存去重标记与待落盘快照，再按预期文件版本写 YAML。打开数据或再次更新时会收尾未完成提交，不启动角色。遇到人工改写时保留本地文件和 `conflicts/relationship-pending-*.yaml`，不会悄悄覆盖。

用 `relationship_recovery_status` 查看待裁决 UID、事件与当前版本。角色暂停后，管理入口可调用 `relationship_recovery_resolve(uid, choice, expected_version)`：`keep_local` 保留当前文件，`apply_pending` 应用待提交快照。先说明实际差异，按用户的处理要求选择，不自行消除冲突。两种选择都会保留已消费的事件标记；如果文件又改过，需重新读取版本。

`data_backup` 现在创建完整 ZIP：配置、全部有效结构化资料、注册图片、SQLite 一致快照和逐文件哈希清单。包含长期去重、动作记录与额度，不含系统 keyring 凭证、登录交接文件、模型权重或缓存。备份损坏或缺图时不报告成功。后台每日备份也使用该格式。

0.4.3 的每日归档在复用前核对完整恢复校验结果：ZIP 结构、逐文件哈希、SQLite 完整性和资料格式。相同归档内容可复用本进程的校验结果，但每次仍重算归档哈希；同长度、同修改时间的损坏不会绕过检查。损坏时重新创建，验证成功后才清理旧归档与历史快照。返回的 `verified/reused/repaired` 分别表示已校验、复用和修复，不能仅凭文件存在认定可恢复。

`data_export` 仍为便于查阅/迁移的内容导出，**不是完整恢复备份**。旧版只有内容的 ZIP 无法恢复完整去重，恢复工具会明确拒绝，不能声称完整恢复。

用户要求恢复时先暂停角色，调用 `data_restore(archive, destination)`，目标必须是当前数据目录之外、尚不存在的新目录。工具验证路径、大小、逐文件哈希、数据库和资料格式后才发布目标目录。原数据保留；恢复出的运行强制暂停并换代，prepared 动作撤销、dispatching 动作转为 uncertain，已发送动作、旧事件去重与已花费用量保留。不自动重发或重新启动。

恢复结果返回新数据目录，不自动修改插件的本机路径。用户明确要求切换到恢复数据时，核对该目录后更新本机插件 `runtime.json` 的 `data` 路径并重新安装插件，使用 `--data <恢复目录> validate` 再核验；切换完成仍暂停。不要把迁移过程的管理对话写成角色经历。

CLI 同样支持：

```text
python -m bili_assistant --data <当前数据目录> backup
python -m bili_assistant restore <完整备份.zip> <尚不存在的恢复目录>
python -m bili_assistant --data <恢复目录> validate
```

当前完整备份限制总解压大小 2 GB、单文件 512 MB。大量文件首次建索引仍需读取/解析；后续进程按内容哈希复用缓存，同长度同时间的修改也会失效。删除或无效 YAML 不沿用旧缓存；坏索引退回读取 YAML，可用 `index_rebuild` 重建。全库搜索仍需哈希扫描；针对已知对象可用 `memory_context.uids` 限定关系记录，其他记忆与知识照常召回。

高频运行检查只读取关键配置、成长状态和关系提交冲突，避免遍历整个记忆库。启动、`state_validate`、管理诊断和备份仍完整校验；单条内容在读取时校验。暂停/归档、非法关键配置和未裁决关系冲突继续阻止派发。不会在每次检查心跳时提前发现所有无关内容文件的格式错误。

普通文本编辑器不参与进程锁。直接手工编辑关系或制作一致备份时，优先暂停角色并避免同时编辑同一份资料。完整备份保存在本机，含个人记忆与平台流水，不随源码提交。
